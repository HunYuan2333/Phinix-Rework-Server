# Neutral operation journal

`IOperationJournalFactory` is available to trusted server plugins through `ExtensionHostContext`, with the same Autofac application scope as the transport. Merely resolving the factory does not create or open a database. There are no host branches for individual businesses.

Call `CreateNew(name)` only after an explicit first-run/import decision. `OpenExisting(name)` never recreates a missing database. Factory names allow ASCII letters/digits, dot, underscore and hyphen, exclude `..`, and map to separate files under `framework-journals/server`. Plugins are trusted; names are not an isolation or authorization boundary. Database errors must not trigger empty-ledger fallback.

`Execute(principal, operationId, canonicalRequest, apply)` holds an immediate SQLite transaction. The caller must authorize the stable principal and supply canonical intent bytes including the operation kind, target/version and complete inputs. Do not include transient session/request IDs in a semantic fingerprint. The journal hashes these bytes with SHA256. A matching committed operation returns its original result without invoking `apply`; different bytes with the same principal/operation ID throw `OperationConflictException`.

Inside `apply`, use `ReadState` / `WriteState` for opaque domain state and `Enqueue` for recipient-bound Pending records. Return the opaque domain result. All changes and the result commit together; only a successful return from `Execute` permits authoritative success publication. Callbacks must be short, synchronous and perform no network sends or external/in-memory authoritative mutations. Handles expire before commit/rollback and cannot cross threads. The journal cannot enforce arbitrary plugin callback execution time; it is not a worker scheduler.

There is no implicit application retry. Concurrent callers of one journal instance are rejected immediately, and SQLite lock contention uses a one-second command timeout. Storage failures disable further writes on that instance; reopening requires inspecting/recovering the authoritative file, not generating another operation ID. A lost response after COMMIT must query/replay the original ID. Neither exceptions nor Unknown authorize refunds.

Initial development limits: identifiers 128 characters, request/result/value 4 MiB each, at most 128 mutations and 8 MiB written per callback. A caught mutation-budget error still aborts the transaction. These are input guards, not measured production capacity or global outbox quotas. Existing durable records are not evicted. Business pagination, delivery attempts/receipts and backlog policy remain separate work.

Schema 1 uses a dedicated application ID and explicit creation transaction; existing unsupported versions fail closed. Future schema changes need migrations, not replacement. The first implementation uses SQLite rollback journaling and `synchronous=FULL`, with per-operation non-pooled connections. `BackupToNewFile` uses SQLite's online backup API, refuses overwrite, and validates the result; do not copy a live database file. New database/backup files use Unix mode 0600. ACLs, network volumes, power failures and supported-platform packaging require their own evidence.

Dependency: fixed `Microsoft.Data.Sqlite` 10.0.13 and locked SQLitePCLRaw dependencies, needed for actual file transactions, native SQLite and online backup without introducing an ORM. See [provider](https://www.nuget.org/packages/Microsoft.Data.Sqlite/10.0.13), [transactions](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/transactions), [backup](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/backup). No shared/client/vendor pin change.

`ReadState` and `TryReadCommitted` expose durable reads without inventing another operation or invoking a callback. A fingerprint conflict still throws. Authorization and namespace ownership remain the caller's responsibility.

The formal Trade plugin now uses this journal at its own persistent storage path, with a staged/hash-checked XML cutover. Its active/terminal/recipient outbox aggregate lives in one state blob, with results in the operations table; it does not use the generic outbox table as a second ledger. See the [Trade integration evidence](../../docs/Server-Upgrade-P3-Trade-Durable-Evidence-2026-10-17.md). These synthetic checks do not establish game asset conservation or reliable game delivery.
