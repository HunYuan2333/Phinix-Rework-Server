# Client inventory and recovery boundaries

Creation and restoration are separate boundaries. RimWorld 1.6 `GenTypes.AllActiveAssemblies` enumerates the game assembly and each active mod's `ModAssemblyHandler.loadedAssemblies`, not every assembly loaded into the AppDomain. Therefore the FillComponents attachment patch alone cannot resolve the saved inventory `Class` node. While inventory is active, an exact-name Harmony prefix on `GenTypes.GetTypeInAnyAssembly(string, string)` supplies `InventoryGameComponent` before native lookup, including when a previous lookup cached null. It leaves every other type lookup unchanged and is removed with the extension's other patches at shutdown. The saved class name, lineage ID and snapshot fields remain unchanged; no inventory reset or automatic relay reward replay is used as a recovery substitute. Reopen an intact original save after updating; a save overwritten after failed restoration may require its backup.

When replaying a local claim/assignment, an unavailable inventory receipt lookup holds the relay cursor and emits the existing throttled recovery message. It must not also emit an unsolicited-claim warning on each tick. Once the exact receipt is available, history updates the displayed claim balance without depositing the reward again; a truly unrequested result still cannot authorize a new reward.

The `builtin.inventory` extension is a client plugin. `InventoryExtension` contains the shared client contract; `InventoryExtension.Client` owns the save-local ledger, journal, extraction, daily plans, and tab. Server projects do not reference inventory. A producer declares a dependency on `builtin.inventory`, registers a versioned codec through `IInventoryRegistrationApi`, and deposits through `IInventoryDepositApi` on the game main thread. Scoped codec and source-presenter registrations must be disposed during extension shutdown. `IInventoryReadApi` exposes status, limits, snapshots, and change events; `IInventoryExtractionApi` owns extraction and schedules. The original `IInventoryApi` remains as a compatibility facade.

Each deposit is an atomic batch with a stable `DepositId`. The ledger hashes its source, item identifiers, versions, quantities, and raw payloads. Localized display labels are presentation metadata and do not affect idempotency. Repeating the same ID and content returns `AlreadyCommitted`; reusing the ID with different ownership data returns `Conflict`. A producer may release its custody only after `Committed` or `AlreadyCommitted`. Codecs decide whether an item can be combined without losing state. Indivisible items retain their complete opaque payload and quantity one.

A producer may attach `OriginKind`, `OriginId`, `OriginUserId`, and `OriginDisplayName` to a deposit. These fields are copied to each resulting entry; the stable kind, event ID, and user ID are included in new deposit receipts. Combinable items merge only when their payload, producer source, and stable provenance identity match, so rewards from different red packets or trades remain separately traceable. Display names are a saved snapshot for readability and do not affect idempotency; stable event and user IDs carry the audit identity. Producers may register an `IInventorySourcePresenter` for their source ID. This keeps producer-specific labels and provenance formatting outside the inventory implementation. Older entries or entries whose producer is absent remain valid and use the generic source fallback.

Contract version 5 adds optional `IInventoryItemPresentationCodec`. Its `PresentItem` reads metadata without materializing game objects and supplies a localized label, a stable codec-local `GroupKey`, and positive `ItemsPerUnit`. The inventory tab groups matching codec/version, item identity, source, origin kind and source user; without a user ID it also retains event separation. Event IDs and all underlying entry IDs remain independent even when displayed in one group. Available totals exclude outgoing reservations. Expand a group to extract or schedule individual records; opaque entries still take whole-record quantities, explicitly labelled with their actual item count. No group extraction, payload rewrite, state equivalence assertion, persistence migration, or protocol change is introduced. Missing or invalid presentation capabilities use standalone legacy rows. UI caches rebuild on ledger, registration, game and language changes, not by restoring every Thing during Draw.

The RimWorld `GameComponent` stores the snapshot and save lineage ID. Because built-in extension assemblies are loaded dynamically from `Common/Extensions`, the inventory extension explicitly and idempotently adds its component after `Game.FillComponents`; it does not rely on RimWorld's earlier type cache discovering the component. A journal under the extension storage root records each newer ledger state and flushes it before `TryDeposit` succeeds. The namespace combines the embedded save ID and canonical save file path, so copying a save to another path does not share subsequent journal entries. A new game must be saved before inventory accepts a deposit. Loading a snapshot older than its journal pauses writes and lets the player restore newer transactions or keep the current save while isolating the abandoned journal branch; it never replays newer entries automatically. An incomplete crash-written tail is isolated while prior verified records remain usable. Corruption in the middle of the journal and invalid snapshots stop writes without discarding the source file. There is no journal truncation during `ExposeData`, because that callback does not prove the complete game save succeeded. Historical records at or before the loaded snapshot may have sequence gaps because operations under another save filename use another journal. These records must still have valid checksums, strictly increasing header/payload sequences, valid ledger states, and identical contents when a record matches the snapshot sequence. The first newer record must be exactly snapshot + 1 and every later record must be contiguous; approval remains required before restoring them. Appends accept only the next committed sequence, including after recovery approval or branch rejection. A verified complete final record without its newline is backed up and given a separator before another append; malformed crash tails are backed up and removed only after snapshot consistency has been checked. No journal format, save field, receipt or reservation migration is needed.

Manual extraction accepts a player-entered quantity and automatically splits it by the codec's stack limit. A request larger than the entry balance is rejected with the available balance instead of being reported as a parse error. Each resulting stack independently follows the journal's reserve, delivery, and completion sequence, so a later failure leaves previously completed stacks committed and the undelivered balance intact. Before reserving anything, delivery rejects disposed maps, missing landing cells, and the entire interval in which `Current.Game.Gravship` remains non-null; RimWorld clears that value in `WorldComponent_GravshipController.LandingEnded`. `IInventoryVerifiedDeliveryCodec` reports delivered, rejected, or uncertain ownership transfer. Rejected delivery restores the reserved balance; uncertain custody remains locked for manual reconciliation. Older codecs remain source compatible and are checked through the same post-delivery custody inspection. Daily plans use the same path.

`IInventoryReservationApi` is the outbound ownership boundary for other client plugins. A consumer reserves one atomic batch under a stable operation ID, receives immutable entry snapshots, and converts them through a business-owned adapter. Active and uncertain reservations reduce `GetAvailableSnapshot()` without deleting the underlying entries. A matching authoritative success commits and deducts the batch; a proven rejection restores it; an unknown result remains locked. Reservation records are journaled with the save and duplicate operation IDs are content-checked. Inventory never references Trade, red-packet types, network packets, or legacy protocol fields.

The cross-save `inventory.deliveryMode` setting selects direct drop pods or save-local inventory for ordinary Trade completion and LegacyRedPacket claims. The inventory extension prompts once when the Phinix window first opens without a saved choice, exposes the same choice in settings, and consumers read it for every delivery so changes take effect immediately. Talent trading is deliberately independent: it has no inventory dependency, keeps its original Pawn serialization/return path, and is not affected by this setting.

Ordinary Trade preserves every authoritative `FrameworkItemPayload` as an indivisible inventory entry. In inventory mode, the client acknowledges only after `Committed` or `AlreadyCommitted`. In direct mode it materializes the complete batch first, validates the same map/gravship boundary, verifies drop-pod custody, and only then acknowledges; rejected or uncertain delivery remains pending. The Legacy Adapter translates old `ProtoThing` completion payloads into the same canonical boundary before Trade sees them. Legacy servers do not support the new durable acknowledgement, so their failed delivery is recoverable only within the current process.

The Trade candidate list also consumes inventory through the reservation API. Inventory asks each entry's registered codec to create an unspawned preview and, after reservation, an all-or-nothing set of temporary transfer objects. Trade immediately converts those objects into its own snapshots and destroys the temporary copies; they are never spawned or delivered to a map. Entries whose codec is missing or cannot materialize losslessly remain extractable only after that codec returns and are not silently degraded into an offer. The existing request token is the ownership commit key: its matching success commits the reservation, rejection restores it, and a send exception after dispatch marks it uncertain. Legacy translation remains inside the Legacy adapter.

LegacyRedPacket also lists available inventory alongside map items, with an Inventory badge. Its displayed and selected quantity counts actual items inside an opaque entry, not just the number of entries. It reserves the selected units (or the entire indivisible stateful entry), converts temporary unspawned objects to its own template, and destroys those objects immediately. All state parts and create are queued atomically; retries retain each event ID and position. Only HTTP acceptance of create after every state part, or the matching create echoed through relay history, transfers custody from inventory to the sender's durable red-packet record. This is relay publication acknowledgement, not a dedicated Trade-server acknowledgement. An unselected part of an opaque stack is returned through an idempotent deposit; stateful rewards and returns are split into legal stacks while retaining every byte of the original state. Claim balances are persisted before consuming each incoming claim. Ordinary unclaimed inventory items return to inventory only after expiry and a successful, drained relay poll covering expiry; a failed or full poll is not proof of empty claim history. Special packet expiry keeps its existing probabilistic return/raid rules.

Sender records use the extension's general storage service and are keyed by a reservation present in the current save, so loading another save cannot automatically release their custody. A 20-second publication timeout becomes uncertain, while a later real acceptance can still resolve it in the same session. Disconnects, game changes and process restarts preserve unfinished sender records as uncertain. Automatic reconciliation of interrupted relay claim history is not implemented: these records stay held for review and are neither resent nor refunded automatically. This limitation is visible in the red-packet tab; it must not be described as full crash recovery. No live Thing reference is persisted by this path.

Rework red packets retain the legacy `create` preview for old clients and send an additive, bounded sequence of `state` parts before it. The state payload is the same compressed Scribe payload used by Trade, is SHA-256 verified, and may be claimed by a Rework client only after every part arrives. Stateful stacks may be divided among recipients by restoring the original state and reducing only `stackCount`; the deterministic claims still sum to the original count. Old Phi clients ignore the additive parts and therefore retain legacy preview-only behavior. State that references an external Pawn or that a third-party component does not expose through Scribe still cannot be reconstructed across saves.
