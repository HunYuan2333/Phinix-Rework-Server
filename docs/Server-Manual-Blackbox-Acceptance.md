## 开始条件

- 通知用户时提供客户端完整安装包、服务端候选、各 DLL SHA256、固定 Common gitlink、游戏版本/Mod 清单和本轮自动化结果；不能直接将不同轮次 Output 中的 DLL 混装。
- 使用两个合成身份、独立服务器目录、两份可丢弃的新测试存档，保存操作前备份。不得使用玩家服务端数据库或凭据。
- 完整交易验收前先完成客户端持久意图/Unknown 查询与展示、现代持久接收边界。这些实现前置已按 RoadMap §41 收口，现在用配套 P3 测试包进行联合验证；真实到账、物化与保存均按实际证据验收。
- 原版、历史 Rework、现代 Rework 分别记录版本/profile；旧端无法表达的能力明确记录“不支持”，不使用现代端结果替代旧端结果。

## 最小操作清单

| 场景 | 操作 | 独立观察/通过条件 |
| --- | --- | --- |
| 正常交易 | A、B 放入可辨认的不同物品，双方查看并确认 | 两边 UI 与最终报价一致；实际游戏物品实例、数量、品质/耐久等对应；双方保存、退出、重启读档后仍一致 |
| 报价竞争 | A 停在旧报价画面，B 改价，A 随后确认 | 旧确认不成交；展示最新报价并要求玩家重新确认；合法托管物品不因拒绝被消费或自动返还 |
| 报价恢复 | 报价成功后重启服务端，再重连双方 | 原 UUID、交易关联及报价保留；不自动变成成交或退款。窗口重建、库存托管与存档恢复另行观察 |
| 离线接收者 | 接收者离线时由另一方完成最后一步，再让接收者登录 | 仅对服务端有明确未发送证据的 Pending 做首次尝试；不伪造到账确认；最终实物与保存结果独立核对 |
| 结果未知 | 提交后丢响应/断线、关窗，再重连和读档 | 明确显示未决结果，保留稳定操作关联；不自动退款、换协议重发或重复物化。本轮游戏检查待执行，按实际命中窗口记录 |
| 接收期间中断 | 分别在接收、物化、保存前后退出游戏并重启 | 持久去重/恢复能说明每次资产归属；不以 ACK 包、通知次数或 SQL 行数代替游戏实物证据。现代库存持久接收/保存回执已有实现，真实游戏结果仍待本轮核对 |
| 旧端尽力交付 | 使用明确版本的原版/历史端，离线后重连，并观察可能已发送后断线 | 区分 Pending/Unknown；只能证明实际观察到的尝试与游戏结果，不能把缺失的可靠 ACK 标为成功；可能已发送不得盲补投 |

每例记录：候选 hash、profile、双方合成标识、交易/operationId、步骤和时间线、实际现象、双边存档重载结果。日志/截图先去除凭据与 session。仅总量相等不足以证明资产归属、实例和保存正确。

发现重复物化、已提交交易丢失、静默退款或结果未知时停止该场景，保留隔离目录和时间线用于诊断；不要通过反复点击、手工补货或自动重试将现象抹平。失败案例修复后复测关联路径，不扩大为无边界重复全量测试。
