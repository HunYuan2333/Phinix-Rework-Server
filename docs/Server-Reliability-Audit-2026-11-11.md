# 服务端可用性与自动恢复核查 — 2026-11-11

本轮围绕普通玩家的交易、重连、排队、短暂数据库争用和插件回调故障，审计当前 Phinix Rework 服务端源码并实施局部修复。它是可靠性核查，不是安全漏洞扫描，也不代表已经在生产环境或真实玩家资产上验收。保留已有工作区修改；没有提交、发布或部署。

## 已确认并修复

| 问题 | 玩家影响 | 现在的行为 |
| --- | --- | --- |
| 恢复分页入队失败后丢失继续执行机会 | 工作队列短暂满后，后续待交付页要等重新登录 | 按连接保留一份继续任务，普通 poll 回调重试入队；一次最多推进四个可执行连接，保持分页边界与队列上限。 |
| 重试等待阻塞其他连接 | 某些连接等重试时，其他玩家恢复可能被拖延 | 只选已到执行时间的任务，轮换入队顺序；会话失效或模块停止时废弃回调。 |
| SQLite 临时读锁被永久记录为存储失效 | 锁已释放，交易仍一直拒绝，需重启 | Busy/Locked 单独归类，不使权威存储永久失败；恢复任务约 1 秒后重新排队。真实损坏、权威文件改变、修订冲突仍保留故障保护。 |
| 提交后内存刷新被临时争用打断 | 下一操作可能看到旧投影，或整个服务被迫停止 | 持有 refreshRequired 状态；任何后续访问先核验原权威并刷新，再继续业务，不用旧投影覆盖新提交。 |
| 登录快照发送失败阻断独立交付恢复 | 玩家已在线，库存交付恢复却未启动 | 快照尝试失败后仍执行独立的待交付恢复入口；原异常仍由外层记录。 |
| 发起者回包/首个参与者通知失败阻断其他参与者 | 交易已经提交，另一方却收不到创建、报价或结束通知 | 创建、报价、状态通知逐项尝试；结束/快照通知按参与者隔离。完成独立通知后继续报告首个异常；不回滚已提交交易、不制造成功回执。 |
| 交易日志订阅者抛异常 | 日志错误可打断真实已提交的交易通知 | 对每个日志订阅者隔离异常，后续订阅者继续。 |
| TLS 事件订阅者抛异常跳过其他维护/断线清理 | 可能留下未清理身份或阻断后续维护 | 与 UDP 的既有行为对齐，逐订阅者隔离；部分失败的新连接关闭，断线回调继续执行其他清理。TLS 仍是既有实验性部署选项，没有改变默认传输。 |
| TLS 通道释放异常跳过 Closed 通知 | 连接已从传输表移除，应用层未收到结束事件 | 通道释放、写任务结束和 Closed 入队使用嵌套 finally；释放失败仍进入后续清理。此异常分支主要以控制流核验，正常断线用真实本机 TLS 回归验证。 |

## 自动恢复边界

- 排队拒绝只保留继续位置，不在网络回调里同步冲刷整个积压。
- 恢复分页中的独立发送失败不挡住同页其他记录；继续扫描约 5 秒后排队。已经尝试过的交付仍由既有交付状态和回执协议决定能否再发，不能把这次继续扫描解释为未知物品自动重投。
- 连接/会话 epoch 改变、退出或模块停止，旧任务不能在新会话执行；订阅在停用时解除。
- 临时读锁不等于数据库缺失/损坏。没有自动重建或切换权威数据库，没有删除余额、恢复旧余额、自动退款或重置 OutcomeUnknown。
- 普通请求正好撞上争用时，本次仍可能返回临时错误；本轮保证后续访问不因这次争用永久锁死，并让待交付恢复继续。并非所有请求都已变为透明重试。
- 旧协议没有可靠持久回执，不能承诺所有未知资产都能无感恢复。原版聊天每连接 256 条去重回执、未决旧交易的保留配额等既有协议约束仍存在；不能通过删除去重或未知记录掩盖这些限制。
