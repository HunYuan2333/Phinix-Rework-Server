# 交易持久化、双方状态与旧端尽力交付

2026-10-16；用户确认的交付范围调整。关联 SV-03/04/31～36/50/52～54、TQ-01/30/31/50/51/60、FR-02/03/09/12。本文是实施契约。历史起点没有 SQLite；2026-10-17 已完成正式 Trade 的事务/导入、Pending/OutcomeUnknown 与弱 ACK 记录子集，见 [实际证据](Server-Upgrade-P3-Trade-Durable-Evidence-2026-10-17.md)。确认版本绑定、Confirmed/durable receipt、原版 Adapter 与真实游戏交付仍未完成，不能把下述完整契约当作已交付状态。P0～P7 依赖不变。

## 目标与共同权威

游戏重启、断线或暂时连接不上不能让已接纳的交易、报价、成交结果或待交付内容凭空消失。服务端统一账本是业务权威；客户端还必须持久保存托管、交付去重及所属存档。不能仅由服务端数据库证明游戏物品已保存到账。

保留原版 Phinix 的普通交易，在旧 wire 可以无损表达物品和操作结果时尽力交付。缺少持久 ACK 本身不再一律禁止普通交易，但它不获得“到账已确认”或“可安全重复交付”的保证。无法表达的 codec/物品/操作仍在 Adapter 整批拒绝。这是有意接受的旧端交付可用性限制，不改变报价原子性、授权、持久提交或现代端确认规则。

所有 profile 共用交易、操作结果、outbox 与 delivery 账本。领域不判断 Legacy/V2，不接收兼容开关；Adapter 只翻译和关联证据，不能自己成交、写第二份业务账本、合成 ACK 或安排一条绕过交付协调器的重发路径。宿主保持中立，恢复由插件通过通用事务/生命周期服务完成。

## 两个相互关联的状态机

交易状态与每位接收者的交付状态分开记录，双方在线状态也不等于交易状态。

- 交易处于协商中时，保存双方完整报价、版本及分别绑定该版本的确认。报价变化使双方原确认失效；旧版本确认必须拒绝。离线/关窗不取消交易。
- 只有同一版本双方有效确认，才在同一事务中记录成交终态、操作结果及双方 outbox。取消也以事务形成终态和需要的返还交付；它不能覆盖已成交结果。终态保留用于重连查询和幂等。
- 每份交付绑定 deliveryId、接收者稳定 UUID、交易结果、物品 hash 和可验证的存档范围（协议有证据时）。不以当前连接 ID 代替接收者，不把 A 的交付证据用于 B。
- “成交已提交”与“A/B 已持久接收”分别展示/查询。快照、成功排队、套接字发送和传输层确认都不能证明游戏保存到账。

| 交付状态（拟议） | 进入条件 | 后续行为 |
|---|---|---|
| Pending | 已提交且尚未开始任何可能发送的尝试 | 离线保留；同一身份 Ready 后尝试；服务端重启仍保留 |
| Dispatching | 已先持久记录 attemptId 和发送边界，再进入传输 | 不允许第二个 worker 并行派发同一交付；不把此状态当作送达 |
| OutcomeUnknown | 已可能发出但无持久接收证据，或恢复发现 Dispatching | 保留原 payload、主体与尝试证据；不自动退款/取消，不盲目应用层重发 |
| Confirmed | 接收主体针对 deliveryId 提供有效持久 receipt，且服务端提交成功 | 不再派发；重复 receipt 幂等；历史结果仍可查询 |

若能够独立证明尝试在进入传输前已失败、绝无任何字节进入发送路径，允许记账后回到 Pending。连接检查与实际发送之间可能断线；普通异常、超时、单独 `TrySend=false` 或连接状态快照不能直接作为“确定未发送”的证明。产品接入时逐一核对传输实现。底层同一次尝试的传输重传与新建应用层交付尝试分开记录。

先写 Dispatching 再发包会留下“可能实际没发出”的崩溃窗口；旧端恢复时保守归为 OutcomeUnknown，不能用先发后记账制造不可见重复窗口。现代端能够证明持久去重时，可用同一 deliveryId 重试并得到原 receipt；重试不产生新的资产结果。生产普通 peer 不能触发故障 hook。

## 旧端支持范围

1. 未完成交易：重启/重连后按同一 UUID 同步权威报价与确认状态；不能把旧端客户端列表缺失当作交易被取消。需核对旧端实际恢复事件与 token 行为。
2. 对方离线：服务端保留 Pending；重新上线并通过身份校验后，再尽力发送兼容的原版交付包。原版建交易是否允许离线接收方仍是独立准入决策，不凭本条自动开放。
3. 已尝试但结果不明：保留 OutcomeUnknown；普通登录、超时、进程重启不重置它，也不自动补发或退款。旧端不能提供持久 receipt 时，不自动提升为 Confirmed。后续核对必须有独立证据；本轮不新增自动人工赔付/强制重发入口。
4. 未升级 Rework 单独核对能力，不能因为现有包名含 ACK 就假设有持久去重/游戏存档证据。实际满足证据的端可走统一 receipt 路径，无法满足者保留未知。
5. 旧端/现代端混合交易分别记录双方交付。一方 Confirmed 不制造另一方 Confirmed，不回滚已提交成交。物品无法被另一方无损表达时，在资产改变前整批拒绝。

旧端“尽力交付”允许最终保留未知状态，不能承诺每次自动最终到账。现代端发布的可靠交付承诺不因此降低。

## 回归与阶段退出

2026-10-16 加速范围更新：下表保留完整扩展目标；当前必须执行的子集以 [RoadMap §14](Server-Upgrade-Roadmap.md#14-加速版最小验收与后续执行) 为准。先做真实 DB、事务幂等、正常重启、提交前后与一次强杀恢复、旧端 Pending/未知保留的必要检查；不先实现所有 faultId、barrier、调度和系统故障矩阵。状态与资产语义保持，首版不承诺断电/存储灾难零丢失。

| 范围 | 必须实际执行的证据 | 阶段 |
|---|---|---|
| 双方报价/版本 | A 确认后 B 改报价；迟到确认、重放及整批引用拒绝 | L1 独立模型、L2；P1/P3 |
| 未完成交易恢复 | 两端报价，客户端重建/重登，服务端强杀/重启，独立读 DB 并核对双方视角 | L2 SQLite、L3 三 profile；P3/P5 |
| 离线待交付 | 已提交且接收方离线；重启保持 Pending，原身份重登只启动一个 attempt | L3/L4；P3/P5 |
| 发送边界 | 派发记账前/后、实际调用前/后、响应丢失的固定 faultId/barrier/强杀 | L4；P3，旧 runtime 在 P5 |
| 旧端未知保留 | 发送后断线/重登/重启，不自动重复、退款、删除或伪 ACK；双方状态独立 | L3/L4 原版与未升级 Rework 分别验证；P5 |
| 现代 receipt | 物化/存档/ACK 丢失，持久去重，同 deliveryId 重试与主体错配拒绝 | L2/L3/L4；P3/P4，游戏实测 P6 |
| 实际游戏重启 | Thing/库存/存档/托管数据在同一存档恢复，工坊更新保留身份 | P6；不能由 Headless 代替 |

用户反馈“游戏重启后交易丢失”作为待复现缺陷，当前未知 profile/具体版本/成交阶段及是否伴随服务端重启，不能先断言根因。现有原版源码有 active-trade 登录同步和文件 Save/Load，但发送完成包后移除 pending notification；当前 Framework store 也只有 XML 快照，尚不能满足上述事务保证。

本轮原版模块 UDP 报价证据见 `Tests/Fixtures/OriginalTrade`。它证明 token 真实回执、双方视角、空报价形状，以及原版客户端模块销毁后以持久凭据重登恢复同 UUID/交易/双方报价；没有验证真实游戏重启、服务端进程恢复或成交交付。本契约在实施过程中由对应故障测试和真实客户端证据逐项关闭。
