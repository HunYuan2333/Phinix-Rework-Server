## 1. 核心原则

### 1.1 插件平权

Chat 和 Trade 与第三方 submod 地位相同。不存在"官方超级公民"：

- 同一套发现路径（反射扫描 `IPhinixExtensionModule`）
- 同一套注册路径（`Register(builder)` → `RegisterApi<T>()` / `AddClientMessageHandler()`）
- 同一套激活路径（`Activate(hostContext)` → `Shutdown(hostContext)`）

**反模式**：宿主为某个插件保留专用接口解析、专用启动分支、专用 UI 入口。

### 1.2 host 不依赖插件

宿主只引用 `ClientExtensionAbstractions`（通用契约层），不引用任何插件的 Contracts 工程：

- `Client.csproj` 的 ProjectReference 中**禁止出现** `ChatExtension`、`TradeExtension` 或任何插件工程
- 宿主通过 `ResolveExtensionApis<T>()` 动态收集插件能力，不做类型强绑定
- 插件可以依赖 host，反过来不行

**反模式**：`Client.csproj` 显式引用插件工程；宿主代码中出现 `IClientChatService`、`IClientTradeService` 等具体业务接口的类型引用。

### 1.3 host 只做通用服务

宿主提供的基础服务与业务无关：

```
网络层 (NetClient)
扩展发现与生命周期 (PhinixExtensionRegistry, IExtensionActivationPolicy)
通用服务 (IClientSessionContext, IClientSettingsContext, IClientUserDirectory,
           IClientUserEventStream, IClientMainThreadDispatcher, IClientWindowService,
           IClientSoundService, IClientLinkService, IClientEnvironmentService, IClientLocalizationService, IClientExtensionManagementWindowService, IUiTheme, IDisplayMessageSink)
ServerTab（通用壳，收集 IMainTabProvider / IServerSidebarProvider / INoticeBannerProvider / IUiAcceptKeyHandler 动态渲染）
基础 UI (SettingsWindow, CredentialsWindow, ExtensionManagerWindow/ExtensionManagerTab, ExtensionControlSettingsPanelProvider)
```

业务逻辑（聊天、交易、红包……）全部在插件里。宿主不关心当前有哪些业务。

## 2. 软件工程原则

### 2.1 松耦合

模块之间通过接口契约交互，不直接依赖具体实现：

- 插件与宿主通过 `ClientExtensionAbstractions` 中定义的通用接口耦合，不通过具体类型
- 插件间交互由插件自行定义接口并直接调用，框架不充当中介也不阻止
- 新增插件不影响宿主编译，不影响已有插件运行

**判断标准**：能否在不修改 host 代码的前提下，新增一个完整的业务插件（含 Tab、侧栏、角标）？

### 2.2 层次化

系统分为清晰的层次，上层依赖下层，禁止反向：

```
┌─────────────────────────────────────────┐
│  Plugins (Chat, Trade, Third-party)      │  ← 业务层
├─────────────────────────────────────────┤
│  ClientExtensionAbstractions             │  ← 共享契约层
├─────────────────────────────────────────┤
│  Host (Client)                           │  ← 宿主层
│  ├─ 网络 / 认证 / 用户管理               │
│  ├─ 扩展发现 / 生命周期                   │
│  └─ 通用 UI 壳                           │
├─────────────────────────────────────────┤
│  Common (Utils, Connections, etc.)       │  ← 基础设施层
└─────────────────────────────────────────┘
```

- 上层可以调用下层，下层**绝不**反向依赖上层
- 同一层内的模块尽量保持独立，减少横向耦合
- 每层只暴露该层职责范围内的接口，不泄露内部实现细节

**反模式**：`Common` 编译 `../../Server/*.cs` 源码；宿主代码直接访问插件内部类型。

### 2.3 减少硬编码

凡是可能随业务变化的，通过合约抽象，不写死在宿主：

- Tab 内容 → `IMainTabProvider`，不硬编码"聊天 Tab / 交易 Tab"
- 侧栏内容 → `IServerSidebarProvider`，不硬编码"用户列表面板"
- 角标 → `IBadgeProvider`，不硬编码"未读消息数"
- 消息处理 → `module → Kind → MessageType → handler` 动态路由，不针对特定消息类型硬编码分发
- 事件通知 → `IClientUserEventStream`，不针对特定插件提供专用事件桥接

**判断标准**：新增一个业务能力（如邮件、公告、任务），宿主代码改动是否为零？

### 2.4 防御性编程与边界检查

所有外部输入（网络数据包、用户界面输入、外部配置、第三方 Mod 数据）均视为不可信输入源：

- **边界集中校验**：在系统边界（UI 控件、网络反序列化入口、配置读取点）进行格式、长度和取值范围的合法性校验
- **数值边界与防溢出**：数值解析统一使用带防御的解析方式（如 `int.TryParse` 配合 `Mathf.Clamp`），杜绝因整型溢出（如输入超大值或负数）破坏内部计算
- **内部不变性**：核心领域层对空引用、集合越界和除零进行防御性断言或提前返回，不依赖对端和调用方的绝对自觉
- **非法输入快速处置**：非法输入在边界处拦截、截断或回退至安全默认值，严禁未捕获异常导致主循环或网络管线中断

**反模式**：直接使用未加限制的强制转换或 `Parse`；假设网络对端发来的数值一定在业务合法区间；输入异常直接抛出未捕获异常导致界面或管线崩溃。

**判断标准**：输入超大数值（如 `int.MaxValue`）或畸形字符串时，系统能否静默钳制或优雅报错，而不是抛出未处理异常？

### 2.5 生命周期对称与重入安全

模块生命周期必须正确响应宿主游戏会话（读档、切档、返回主菜单、重新连接）：

- **配对清理**：任何在会话期间建立的事件订阅（`+=`）、定时器、后台线程与文件句柄，必须在会话结束或模块关闭时对称清理（`-=`、`Dispose`）
- **无状态跨会话**：退出到主菜单时，必须彻底清理对当前游戏世界、地图实体的所有静态引用和缓存，防止旧世界对象无法被 GC 回收造成内存泄漏
- **幂等重新初始化**：组件必须支持多次“读档 → 回主菜单 → 再读档”的反复重入，单例初始化与事件注册必须具备防重复机制

**反模式**：在静态字典里长久持有世界实体；退出存档时不注销事件监听，导致再次进档时同一事件被重复触发多次；依赖进程重启来重置状态。

**判断标准**：连续进行 5 次“载入存档 → 退出至主菜单 → 载入新存档”，内存基线是否平稳？事件监听是否未发生重复触发？

客户端 framework 的构造只建立依赖；宿主在游戏主线程完成服务准备后显式调用 `Start()`。运行中重复 Start 不重复激活；Stop/Shutdown/Dispose 为终结性的幂等关闭，重新启动需创建新实例。Registry 在 Register/Activate 部分失败后也调用模块 `Shutdown`，因此清理必须容忍初始化未完成。依赖消费者先于提供者停止，模块登记随后撤销；消费方不释放借用的宿主服务或跨插件 API。正常游戏退出通过 Unity 主线程退出事件清理；ProcessExit 只释放无游戏依赖的宿主资源。

### 2.6 最小侵入原则与生态隔离

作为插件运行在宿主游戏与上百个 Mod 构成的复杂生态中，应主动降低对外部环境的干扰：

- **挂载点优先**：业务接入优先使用通用挂载点（Tab、Sidebar、Handler、Settings），非必要不使用侵入式补丁（Harmony）
- **补丁最小化**：必须使用补丁时，坚持最小切片原则（前置 Prefix / 后置 Postfix 优先，非必要绝不使用 Transpiler 重写大方法）；仅拦截底层原子方法，不侵入高频顶层循环
- **命名空间隔离**：公开的 DefName、配置键、网络标签必须带统一前缀（如 `Phinix_`），避免与宿主或其他 Mod 发生命名冲突
- **不污染全局共享状态**：不得随意修改或无序消耗宿主游戏的全局状态（例如共享随机数流 `Verse.Rand`、全局静态上下文）

**反模式**：动辄 Transpiler 游戏的核心顶层更新逻辑；使用没有唯一前缀的通用 Def 名称导致与其他 Mod 冲突。

**判断标准**：在包含上百个其他 Mod 的环境中加载运行，是否存在命名冲突或导致游戏原生行为异常？

## 3. 关键设计决策

### 3.1 动态 Tab 机制

通信层和 UI 层使用同一套动态分发模式：插件注册 handler/provider → host 通过接口发现和收集 → 按排序键（Priority/TabOrder）路由。

- `ServerTab` 是纯容器，不包含任何业务 UI
- `ServerTabButtonWorker` 聚合所有 `IBadgeProvider`，只显示第一个有内容的角标
- 新增加 Tab/侧栏只需实现对应接口并在 `Register()` 中注册

宿主向所有扩展提供 `IClientExtensionManagementWindowService`，打开宿主拥有的扩展管理窗口，复用 `ExtensionManagerTab` 作为内容。宿主不再注册专用“扩展”主 Tab；商店扩展通过通用 `IMainTabProvider` 提供自己的页面并调用管理服务。即使商店不存在或被禁用，宿主模组设置也保留恢复入口。所有已发现扩展（包括内置）的启用、停用仍沿用重启生效策略。

### 3.2 通信管道三分类

框架通信分为三条主链，各司其职：

| 管道    | 职责         | 示例                    | 当前状态       |
| ------- | ------------ | ----------------------- | -------------- |
| Message | 用户可见消息 | 聊天消息、系统通知      | ✅ 完整可用    |
| Command | 后台控制指令 | 交易创建/更新、快照同步 | ✅ 完整可用    |
| Item    | 物品数据载荷 | 交易物品编码/解码       | ✅ P0 完整可用 |

> **关于 Item 管线当前状态（2026-06-21 更新）**：P0 已补全。服务端三段链（`IServerInboundItemInterceptor` → `IServerDefaultItemHandler` → `IServerItemObserver`）就绪；Client 端 `KindItem` 独立路由 + `IClientIncomingItemHandler` / `IClientOutgoingItemHandler` / `TryHandleOutgoingItem` 就绪；`IItemCodec` 注册后即被管线消费；Trade 现有 Command 嵌套路径兼容不变。详见《Item管线补全实施方案.md》。

新增消息类型时，先判断属于哪条管道，再选择对应的 handler 接口实现。

### 3.3 插件间交互

插件之间的协作由插件自行负责，框架不充当中介：

- Chat 需要发起交易 → Chat 直接引用 `TradeExtension` 的 Contracts，调用 `ITradeRequestApi.CreateTrade()`
- 两个插件需要共享数据 → 各自定义接口，通过 API registry 互相解析
- 框架的作用只是提供发现机制（API registry），不承担业务协调

### 3.4 通用事件流取代专用桥接

插件不通过宿主专为其定制的桥接接口获取宿主事件，而是消费通用事件流（`IClientUserEventStream`、`IClientMainThreadDispatcher`、`IClientSettingsContext`、`IClientSessionContext` 等）。具体接口列表及其用法见《附属 Mod 开发者指南》§8。

**反模式**：宿主定义 `IChatUiEventSink`、`ITradeUiHostContext` 等插件专用接口，每次新增插件就新增一套。

### 3.5 错误隔离与重试机制

网络处理、消息解析、扩展执行中的单个失败**不得**中断整体管线或导致服务崩溃。框架对各类错误采取分层隔离策略：

**管线内隔离：**

- 单个拦截器/处理器抛出的异常由 PipelineRunner 捕获并记录，管线继续处理下一个候选者
- 单个消息的解析失败（如 Protobuf `ParseFrom` 异常）仅跳过该消息，不影响同一帧内的其他消息
- 扩展的 `Activate()` / `Shutdown()` 失败不影响其他扩展的生命周期

**网络层韧性：**

- 关键握手包（Hello / Auth / Login / ExtendSession）发送失败必须主动断开对应连接，防止客户端无限等待
- 非关键消息发送失败记录错误日志并通知调用方（通过返回值或回调），不静默丢弃
- 连接断开时立即清理关联的 session、用户状态、事件订阅，不依赖超时定时器兜底

**重试策略：**

- 客户端连接失败应提供明确的错误信息（区分"网络不可达""认证被拒""协议不匹配"），而非笼统的"连接失败"
- 客户端未连接时发送的消息应触发可观测的告警（日志级别 Error 或回调通知），不静默丢弃
- 服务端向特定连接发送失败时区分"连接已断开"和"发送超时"——前者触发清理流程，后者可考虑重试

**反模式**：catch-all 静默吞掉异常；后台线程异常不通知主线程；发送失败仅写一行 Debug 日志而调用方无感知。

### 3.6 反压与资源边界

所有无界队列必须有容量上限，防止生产者快于消费者时内存无限增长：

- 消息显示队列（`displayMessages`）：上限 1000，超出时移除最旧的条目并记录 Warning
- 主线程调度队列（`pendingActions`）：上限 500，超出时丢弃并记录 Error
- 扩展管理面板日志缓冲（`extensionLog`）：上限 300 条（`MaxExtensionLogEntries`），由 `ExtensionLogVersion` 版本号触发只读快照重取，杜绝每帧 GC 分配
- 聊天历史同步：分批发送（每批 50-100 条），不在单次 poll 周期内阻塞发送全部历史

持有 `Timer`、`NetManager`、`Thread`、`FileStream` 等 `IDisposable` 资源的类必须实现 `IDisposable` 并在 `Shutdown` / `Dispose` 中释放。事件订阅（`+=`）必须在对应的 `Shutdown` 或 `Dispose` 中配对取消（`-=`），不依赖进程退出作为终极清理手段。

### 3.7 插件不得绕过通信管线直连底层传输

插件与服务器通信时，**必须通过框架定义的 handler 管线**（`IClientMessageHandler`、`IClientCommandHandler`），**不得**直接调用 `IFrameworkClientTransport.SendFrameworkPacket()` 或 `ILegacyModuleTransport.Send()` 绕过管线。

**为什么：**

- handler 管线是框架实现"插件平权"（§1.1）的机制 —— Priority 排序、拦截、替换、回退都依赖 handler 依次执行
- 插件直接发 FrameworkPacket 绕过管线 = 该协议包**跳过所有其他插件的 handler**。如果另一个插件（如 LegacyAdapter）通过 Priority 排序尝试拦截流量做协议翻译，它将完全无效
- 一个生态位良好的插件（如消息审计、内容过滤、协议适配）不应该因为其他插件"走了捷径"而失效

**正确做法：**

- 出站消息：通过 `IClientMessageHandler.HandleOutgoingText()` 返回 `FrameworkPacket`，让 `PhinixFrameworkClient.TryHandleOutgoingMessage()` 统一发送
- 出站命令（Trade等）：通过 `IClientCommandHandler` 管线，或通过 `IFrameworkClientLifecycle.CompatibilityMode` 判断当前模式后决定路由策略
- 入站消息：由框架从 `NetClient` 接收后分发给 handler 管线；插件不自行注册 `NetClient` handler 拦截入站（Legacy 协议适配除外，因为 Legacy 入站完全不在 Framework 管线上）

**唯一例外**：Legacy 协议适配器可以通过 `ILegacyModuleTransport.RegisterHandler()` 注册原始模块 handler，因为 Legacy 入站数据完全不经过 Framework 管线（老服务器发送的是 `"Chat"` / `"Trading"` 模块包，不是 `"PhinixFramework"` 包）。

**判断标准**：任意一个新插件能否通过 Priority 排序插入到通信管线中，拦截/修改/替换消息而不需要其他插件主动配合？

### 3.8 日志与可观测性

框架通过 `ILoggable` 接口（定义于 `Common/Utils/ILoggable.cs`）提供统一的日志事件机制。Host 内部组件（`NetClient`、`ClientAuthenticator`、`UserManager`、`PhinixFrameworkClient` 等）实现此接口以产生日志事件，host 在启动时统一订阅汇聚。

**插件侧当前约定**：插件通过 `hostContext.Log` 回调（`Action<string, LogLevel>`）上报日志。此回调由 host 在构建 `ExtensionHostContext` 时注入，指向与 `ILoggable` 事件相同的日志出口。**当前官方扩展（Chat/Trade）使用 `hostContext.Log`，尚未直接使用 `ILoggable`。后续将统一迁移到插件的 `ILoggable` 支持。**

没有任何代码可绕过框架日志机制自行写入控制台或文件。

**日志级别约定：**

| 级别      | 含义         | 使用场景                                   |
| --------- | ------------ | ------------------------------------------ |
| `DEBUG`   | 开发诊断信息 | 管线消息路由细节、扩展加载过程、临时调试   |
| `INFO`    | 正常运行信息 | 连接建立/断开、扩展激活/关闭、配置加载     |
| `WARNING` | 可恢复的异常 | 队列溢出、消息解析失败但管线继续、重试成功 |
| `ERROR`   | 需关注的故障 | 握手包发送失败、扩展激活失败、发送超时     |
| `FATAL`   | 服务不可继续 | 关键资源耗尽、不可恢复的状态损坏           |

**日志内容规范：**

- 所有异常日志必须附带 `Exception` 对象（如 `LogEventArgs` 支持），不能只记录 `ex.Message`
- 网络消息日志**不得**记录明文 token、密码、密钥等敏感字段；协议包内容记录需脱敏
- 消息级日志（如管线观察器 `IServerMessageObserver`）应包含消息类型标识，便于按模块过滤

**生产环境最低可观测性要求：**

- 当前连接数（`connectedPeers.Count`）应在日志中周期性可见或可通过命令查询
- 消息吞吐量（入站/出站 QPS）应可通过 `IServerMessageObserver` 汇总后接入日志
- 错误率：至少区分"管线内业务错误"和"网络层传输错误"，分别统计

**客户端侧特别约定：**

- RimWorld 控制台会吞掉部分 stdout 输出，客户端日志不应仅依赖 `Console.Write`——应通过 `hostContext.Log` 回调（当前）或 `ILoggable` 事件（后续迁移目标）桥接到宿主的标准日志路径
- **Release 构建分级过滤**：在 Release 构建下，客户端 `ILoggableHandler` 与扩展日志缓冲区过滤 `DEBUG` 级日志（管线路由细节、命令派发、交易快照广播等降为 DEBUG），避免频繁聊天刷屏 RimWorld 控制台；`INFO` / `WARNING` / `ERROR` 保持输出；仅在 Debug 构建或开启开发者模式（DevMode）时显式展示 DEBUG 级日志
- 宿主扩展管理面板（`ExtensionManagerTab`）内置 300 条上限的日志查看器，支持按时间戳和日志级别着色展示，便于游戏内诊断排查

**反模式**：插件绕过日志机制自行 `Console.WriteLine`；异常日志只写 `ex.Message` 丢弃堆栈；生产日志级别设为 DEBUG。

### 3.9 显式状态机与超时自愈

多步骤异步交互与网络通信流程必须采用有限状态机（FSM）管理：

- **形式化转移**：状态集合与允许的转移路径集中、显式定义，禁止使用零散布尔变量组合出隐式状态
- **超时自愈机制**：凡处于等待远端确认或异步回执的中间状态（如 `Pending`），其生命周期必须严格有界；必须具备确定性的超时检测，超时后自动降级或标记失败，禁止因网络丢包导致流程永久卡死
- **状态驱动表现**：状态机负责维护业务状态，UI 仅作为观察者读取状态并展示，禁止 UI 代码绕过状态机直接强行修改内部状态

**反模式**：Vibe coding 随手加 `isWaiting`、`isProcessing` 等隐式布尔标志位；异步请求无超时处理，对端未响应导致 UI 永久转圈且无法取消。

**判断标准**：系统是否能用一张明确的状态转移图完整描述所有流程？模拟网络完全丢包时，系统能否在指定超时后自动恢复可用状态？

### 3.10 数据缓冲与按需消费

接收外部数据与创建游戏内高开销对象（UI 元素、游戏实体）必须严格解耦：

- **缓冲优先**：突发到达的大规模或批量数据，优先存入轻量本地缓冲或轻量数据结构暂存，严禁在单帧内瞬时触发大规模对象实例化（如一次性空投生成成百上千个实体）
- **按需与分批处理**：大列表界面必须结合视口裁剪（Virtual Scroll），游戏实体生成采用按需提取或时间预算分批调度（Time Slicing），平摊主线程开销
- **有界队列防压垮**：所有接收队列和任务调度队列必须设定容量上限与超限处置策略（丢弃、合并或告警），防止网络涌入时内存无序膨胀

**反模式**：网络收到大量物品数据时，立刻在一帧内向地图连续生成全部物品，导致物理引擎、寻路网格和渲染卡死；无界队列在网络高频涌入时耗尽内存。

**判断标准**：一次性接收大量数据或批量物资时，游戏帧率是否保持平稳，未出现明显停顿或雪崩？

### 3.11 存档韧性与向前容错

模组数据持久化（如 `ExposeData` / 序列化）必须遵循“存档安全第一”原则：

- **向前兼容与默认值兜底**：字段新增或移除时，旧存档缺失该字段必须自动回退至安全默认值，不得因反序列化失败导致存档损坏
- **局部故障隔离**：反序列化单项数据（如单条记录、单个物品缓存）失败时，仅跳过并记录警告，严禁抛出未捕获异常阻断游戏主存档的正常加载
- **卸载平稳**：当玩家禁用或移除 Mod 后，持久化数据中不应残留导致宿主主引擎抛出致命异常的幽灵实体

**反模式**：反序列化缺少字段直接抛出异常导致整个存档加载流程中断（炸档）；Mod 禁用后存档报错无法继续游玩。

**判断标准**：手动在存档中删除或损坏本 Mod 的某一字段，游戏能否正常载入存档并在日志中给出降级提示？

### 3.12 客户端模块装配

客户端宿主通过 `IExtensionBuilder.HostContext` 提供 `IClientCompositionFactory`。官方和第三方模块均可在 Register 中创建自己拥有的 `IClientCompositionScope`。模块发现和无参模块构造保持原有路径；普通服务的必需依赖改为构造参数。中立的 `IClientCompositionBuilder` 仅提供类型注册 `Register<TService, TImplementation>()` 和借用 `Borrow<T>(instance)`。服务/API/UI 在装配入口 Resolve 后，通过现有 builder 发布；业务服务和逐帧 UI 不访问容器。

Client/Composition 拥有 Autofac 8.4.0 及锁定的依赖图。Common、插件契约和插件实现项目不引用 Autofac。每项注册在本模块内为单实例，构造不启动工作。Activate 显式启动订阅/任务；Shutdown 先使模块回调失效并解绑模块事件，再释放 scope。拥有的资源必须提供同步 IDisposable 清理，只有异步释放的类型会在构造前被拒绝。拥有的 IDisposable 服务负责停止和取消自己的工作；受保护的释放路径逐项报告异常并继续释放依赖。借用的宿主服务和跨插件 API 不会被释放。创建、注册、解析、释放均要求游戏主线程；已释放 scope/factory 不可重启。宿主在注册表停止后兜底释放剩余 scope。

Chat 是首个采用者。消息适配器、UI 上下文、用户列表、公告侧栏仅在显式 Start 时订阅，释放时解绑，包含部分 Start 失败。排队的提及/旧协议通知在执行前检查模块状态、连接代次和捕获的游戏实例。Chat 退出在主线程取消图片请求并释放缓存纹理。可选 Trade API 仍由模块装配入口提供延迟借用操作。其他模块在各自迁移前继续使用现有装配方式。

主包在 Common/Assemblies 中独占一份 Phinix.ClientComposition 和八个支持 DLL；Memory/Unsafe/Vectors 的编译引用与打包版本必须一致，托管插件不得重复携带这些宿主资产。部署或回退应成套替换宿主、抽象、Utils、Chat 和运行库，仅换 Chat DLL 不足以匹配本批。新增契约保持现有抽象程序集版本 1.8.0.0；使用新接口的模块需要对应宿主构建。编译和控制台回归通过不代表 Unity 加载或其他模组兼容已经验证。

新客户端作者继承 `ClientExtensionModule`，覆写 `Compose(IExtensionBuilder)`（ClientExtensionAbstractions 1.9）。显式且不可覆写的共享 Register 桥接先检查宿主装配服务，再由普通注册表调用 Compose。Chat 已接入；构造保持被动，Activate/Shutdown 及 scope 所有权仍需明确。迁移期间原直接 Register 模块与服务端路径保留。托管元数据仅识别可信客户端契约/基类的程序集身份，不开放任意外部继承。API/CLR 版本 1.9 阻止新作者绑定旧契约程序集；部署匹配的完整主包。

F4-H 开发状态：维护中的 Chat/Inventory/Trade/Store/LegacyAdapter 及两个示例已使用 Compose。客户端直接 Register 已弃用，LegacyClientExtensionModule 是带 Obsolete 的源兼容适配器，实际登记的旧客户端模块每次启动收到一次迁移警告；共享服务端注册表不变。计划首个稳定弃用版本为宿主 0.9.8，宿主 1.0 / 客户端抽象 2.0 在独立插件迁移、分发/回退与游戏门槛通过后移除旧入口；不是已经发布的版本提升或移除。1.9 组合契约/运行库组合为冻结候选，尚未通过的游戏/边界门槛须明确保留。

### 3.13 商店操作状态转移

内置商店在内部操作模型中使用锁定版本的 Stateless。共享契约、宿主和业务服务不暴露库类型。控制器在同一锁内串行执行状态转移和快照发布；操作代次与令牌身份拒绝过期结果及进度。转移不执行下载、安装、界面操作或持久化写入。

取消后保持忙碌，直到工作任务退出。取消后的临时成功结果转为 Canceled；获得权威持久提交成功确认的安装或状态修改保留真实结果。Dispose 先发布终态 Stopped，再调用取消回调，迟到结果无法恢复控制器。现有安装日志、恢复及校验服务仍是权威。Installed 必须获得安装服务成功响应及新库存读取；下载进度满格不足以表示安装成功。Common/Assemblies 只有一份匹配的 Stateless DLL，托管包不能替换它。部署完整匹配包；控制台测试不能证明游戏内加载正常。

扩展管理还展示未被发现的已保存禁用模块 ID，卸载后仍可恢复。这些仅为界面恢复条目，不加入注册表/发现结果，也不创建模块实例。明确恢复某条目只改变对应模块设置；安装仍要求启用模块意图并通过现有所有权及程序集检查。包期望状态与模块禁用数量分别展示。

## 4. 边界规则

### 4.1 引用方向

```
Client → Common (shared contracts & abstractions) ← Server

禁止：Common → ../../Server/*.cs
禁止：Common → ../../Client/*.cs
禁止：Client → 具体插件工程 (ChatExtension, TradeExtension, ...)
```

### 4.2 Common 能放什么

- 协议（protobuf contracts, packet DTO）
- 抽象（extension module contracts, handler contracts, API registry abstractions）
- runtime-neutral 工具（序列化、文本处理、基础日志接口）
- 双端都需要且不绑定特定运行时的基础设施

### 4.3 Common 不能放什么

- 业务处理器（聊天、交易、或任何具体业务逻辑）
- 服务端状态管理器
- 客户端 UI 模型
- 任何 client-only 或 server-only 运行时实现
- host 对官方插件的特殊假设

### 4.4 判断标准

> 如果一段代码移到某一端（Client 或 Server），另一端**完全不受影响**，那它就不该在 Common 里。

### 4.5 Common 源文件共享模式（现状过渡）

当前部分端专属实现（`ClientAuthenticator.cs`、`NetClient.cs`、`NetServer.cs`、`ClientUserManager.cs` 等）物理上存放于 `Common/` 目录下，但通过 `.csproj` 中的 `Compile Remove` / `Compile Include` 链接机制确保**编译归属是单端的**——Common 的 `Connections.csproj` 排除 `NetClient.cs` 和 `NetServer.cs`，由 `Connections.Client.csproj` 和 `Connections.Server.csproj` 分别通过路径链接编译。

此模式是过渡态，物理位置 ≠ 编译归属。判断文件是否越界的标准是**编译归属**而非物理路径：

- 一个文件被 `Common/Authentication/Authentication.csproj` 编译 → 属于 Common
- 一个文件仅被 `Client/Common/Authentication.Client/Authentication.Client.csproj` 编译 → 属于 Client，不管它物理上放在哪里

**目标态**：端专属实现物理移动到各自端目录下，Common 目录中仅保留真正 runtime-neutral 的源文件。此调整应在程序集拆分（§5.2）完成后进行。

## 5. 目录与程序集约定

### 5.1 命名与排序

DLL 文件名使用零填充数字前缀确保字符串序 = 加载序。当前构建产物目录结构与编号分配如下：

```
Client/
  Common/
    Assemblies/                          ← 仅框架基础设施与核心抽象 DLL
      01-LiteNetLib.dll                  ← 第三方网络库
      02-Protobuf.dll                    ← 序列化库
      03-Utils.dll                       ← IPhinixExtensionModule, framework 基础
      04-Connections.dll                 ← 共享网络类型
      05-Connections.Client.dll          ← 客户端网络实现
      06-Authentication.dll              ← 共享认证契约
      07-Authentication.Client.dll       ← 客户端认证实现
      08-UserManagement.dll              ← 共享用户管理契约
      09-UserManagement.Client.dll       ← 客户端用户管理实现
      10-ClientExtensionAbstractions.dll ← UI 抽象与通用 host 契约
  1.6/
    Assemblies/
      13-PhinixClient.dll                ← 客户端宿主主程序集
  Common/
    Extensions/                          ← 插件独立目录（已与 Assemblies 分离）
      08-ChatExtension.dll               ← Chat 领域契约
      09-TradeExtension.dll              ← Trade 领域契约
      10-InventoryExtension.dll          ← 库存领域契约
      10-LegacyAdapter.Client.dll        ← Legacy 协议适配插件
      11-ChatExtension.Client.dll        ← Chat 插件
      11-InventoryExtension.Client.dll   ← 库存客户端插件
      12-TradeExtension.Client.dll       ← Trade 插件
      17-PluginStore.Client.dll          ← 内置插件商店
```

新增 DLL 时按依赖关系分配编号。当且仅当字符串序保证所有依赖先于被依赖方加载，RimWorld 的 `ModAssemblyHandler` 才不会抛出 `ReflectionTypeLoadException`。

红包和人才贸易是独立可选插件，主解决方案与主发行包不再包含它们。主包构建只清理生成输出中已退役的平铺 DLL、sidecar 和专属语言资源，不删除玩家设置、存档或托管安装目录。它们仍使用普通发现/注册路径；既有程序集/模块名称中的 Legacy、BuiltIn 或 builtin 前缀不表示继续内置。

### 5.2 发布边界（现状已落地）

官方插件 DLL 与框架基础 DLL 已完成物理分离：

```
Client/
  Common/
    Extensions/          ← 插件 DLL 独立目录（官方插件 + 第三方插件 probe 目录）
      ChatExtension.Client.dll
      TradeExtension.Client.dll
      LegacyAdapter.Client.dll
      ...
    Assemblies/          ← 仅框架基础 DLL（01-10）
  1.6/
    Assemblies/
      13-PhinixClient.dll ← 宿主程序集

Server/
  Extensions/            ← 服务端插件 DLL 独立目录
    ChatExtension.Server.dll
    TradeExtension.Server.dll
```

宿主启动时 `ExtensionAssemblyLoader` 会扫描 `Common/Extensions/`，同时原生支持自动探查所有已激活 RimWorld Mod 的 `Assemblies/` 目录，使得第三方插件既可作为独立 Mod 分发，也可置入 Extensions 目录（详见《附属 Mod 开发者指南》§2.4）。

### 5.3 版本化与 API 兼容

**程序集版本统一：**

所有程序集版本号通过 `Directory.Build.props` 集中管理，不分散到各 `AssemblyInfo.cs` 手动维护。当前各项目版本不一致，需对齐为统一版本。

**Git 标签与发布：**

- 语义化版本（Semver）：`MAJOR.MINOR.PATCH`
    - `MAJOR`：破坏性 API 变更（如接口删除、方法签名改变）
    - `MINOR`：向后兼容的新增（新接口、新方法、新插件挂载点）
    - `PATCH`：纯修复，不改变任何公开 API
- 每次发布打 Git 标签 `v<semver>`，触发 Docker 镜像构建与发布

**Protobuf 消息兼容：**

- 字段编号（field number）是**永久的、不可更改的**。删除字段必须用 `reserved` 保留编号和名称，防止未来重用
- 新增字段只能追加，不得插入已有字段之间
- 枚举值不得删除或重编号——废弃值标记 `[Obsolete]` 或注释，但保留其数值
- 修改消息类型语义时必须创建新消息类型（如 `LoginRequestV2`），旧类型作为遗留兼容保留

**API 废弃生命周期：**

与 §6 Host/Core 增量更新规则配套，`[Obsolete]` 标记遵循以下节奏：

```
标记 [Obsolete] → 至少保留 1 个 MINOR 版本 → 确认无下游引用后移除
```

- 废弃接口必须在 XML 文档注释中指明替代方案（`<summary>Use IXxx instead.</summary>`）
- 移除前应搜索整个仓库及已知第三方 submod 确认无残留引用
- `MAJOR` 版本升级时可以集中清理已到期废弃项

## 6. 渐进式迁移原则

- **每阶段保持可编译、可运行、可验证**。不做"一次性大迁徙"。
- **先收口边界，再做运行时迁移，最后完整插件化**。
- **重构不改行为**。Phase 5 的每次改动（类型移动、引用调整）只改变代码归属，不改变运行时行为。如果行为变了，就是 bug。
- **目录收口先于程序集拆分**。物理目录可以先整理干净，程序集边界可在后续阶段逐步收紧。
- **新代码遵从新规则，旧代码逐步迁移**。新增功能必须满足当前阶段的边界要求；已有代码按优先级逐步迁出。
- **Host 与 Core 仅做增量更新**。对 Host 和 Core 的所有改动必须为增量式——不删除、不移除任何现有公开接口。如需破坏性变更，保留原接口并标记 `[Obsolete]`（或注释 `// outdated`），内部实现可重写但外部行为必须一致。此规则确保下游插件和第三方 submod 不因框架升级而编译失败或运行时断裂。

## 7. 提交与审查 check-list

新增或修改代码时，检查以下几点：

- [ ] host 工程是否新增了对插件的引用？
- [ ] Common 是否新增了 client-only 或 server-only 的代码？如确需新增，是否仅通过 `.csproj` 链接编译归属，而非直接编译进 Common 程序集？
- [ ] 是否硬编码了某个具体业务类型（如直接使用 `IClientChatService`）而非通过通用接口（如 `IMainTabProvider`）？
- [ ] 新增的扩展入口是否通过现有通用挂载点接入（Tab/侧栏/角标/消息处理），还是在宿主里开了新的专用口子？
- [ ] 插件间交互是否直接在插件间完成，而不是通过 host 中转？
- [ ] 字符串排序下的 DLL 加载顺序是否正确？
- [ ] 新增的网络处理/消息解析是否有 try-catch 隔离？单个消息失败是否会中断整个管线？
- [ ] 新增的 `IDisposable` 资源持有者是否实现了 `IDisposable`？事件订阅是否在 `Shutdown` 中配对取消？
- [ ] 新增的队列/缓冲区是否有容量上限？是否处理了生产者快于消费者的场景？
- [ ] 对 Host/Core 的改动是否为增量式？是否删除或移除了任何现有公开接口？如需破坏性变更，是否保留了原接口并标记 `[Obsolete]`？
- [ ] 日志调用是否通过 `ILoggable` 接口上报，而非绕过框架自行写控制台/文件？异常日志是否附带完整的 `Exception` 对象？
- [ ] 是否新增了公开 API？如新增，版本号是否需要升级为 `MINOR`？如修改/移除，是否已标记 `[Obsolete]` 并在文档中指明替代方案？
- [ ] Protobuf 字段变更是否兼容——未重用已删除字段编号、未修改枚举值、破坏性变更是否创建了新消息类型？
- [ ] 外部输入与数值解析是否有范围边界检查（如 `TryParse` + `Clamp`）？是否能防范超大数值溢出？
- [ ] 异步网络流程是否有显式状态机定义？是否有超时回退机制，避免对端不回时永久死锁？
- [ ] 退出到主菜单或切换存档时，事件订阅是否完全注销？静态变量是否断开了对地图实体的引用？
- [ ] 是否新增了侵入式 Harmony 补丁？能否改走现有的通用挂载点？
- [ ] 新增的 Def、配置 Key 是否带有统一的命名空间前缀？
- [ ] 接收外部大载荷数据时是否具备缓冲暂存机制，而非在单帧内瞬时生成大量游戏世界实体？
- [ ] 存档与配置序列化是否有默认值兜底？单项损坏是否会阻断主存档加载？
- [ ] 独立窗口（ServerTab、SettingsWindow、CredentialsWindow、TradeWindow 等）是否使用 `UiScreenSafeArea.ClampWindow` 限制在屏幕可见安全区？
- [ ] 控件与容器布局输出的 Rect 是否做好了非负归一化（防止负宽、负高导致 Unity IMGUI 渲染异常）？
- [ ] 双栏或多栏界面是否声明并执行了空间不足时的降级退化策略（垂直排列或 SinglePane 子 Tab 切换）？
- [ ] 表单与工具栏是否支持动态重排（Inline/Stacked）与溢出菜单（FloatMenu），长翻译与长文本是否配有滚动条或截断 Tooltip？
- [ ] 大型或不确定长度的列表（聊天消息、物品列表、日志）是否使用 `VirtualListLayout` 仅绘制视口可见行？
- [ ] 是否避免了在新增代码中使用已被 `[Obsolete]` 标记的旧版 Flex/TabsContainer 容器？

## 8. 发布前性能与稳定性审查

每个里程碑发布前，对照以下类别逐项审查。审查通过标准：**所有 CRITICAL 项清零，HIGH 项有明确处置计划**。

### 8.1 内存泄漏

**审查要点：**

- 所有 `IDisposable` 资源持有类是否在 `Shutdown` / `Dispose` 中释放？检查对象：`Timer`、`NetManager`、`Thread`、`FileStream`、`StreamReader`/`StreamWriter`
- 事件订阅是否有配对的取消订阅（`+=` ↔ `-=`）？依赖进程退出作为唯一清理手段视为未通过
- 字典/列表等集合在元素移除时键是否匹配？（如 session 字典用 connectionId 做键但 Remove 用了 sessionId）

**检查方法：** 启动服务器 → 连接 5 个客户端 → 断开 → 重复 3 轮 → 检查内存基线是否持续上升。客户端同理：进入服务器 → 切换 Tab → 退出 → 重复。

**反模式**：依赖超时定时器兜底清理本应在事件触发时立即清理的资源。

### 8.2 错误处理

**审查要点：**

- 网络层：`connectedPeers` / `probePeers` 的读写是否有锁保护？后台线程触发的回调是否封送至主线程？
- 管线层：单个拦截器/处理器异常是否被 PipelineRunner 捕获？异常后管线是否继续处理下一个候选者？
- 解析层：Protobuf `ParseFrom`、`Unpack` 等反序列化操作是否有 try-catch？恶意或损坏的消息是否仅跳过而不中断管线？
- 关键握手包：Hello / Auth / Login / SessionExtend 的响应发送失败是否导致了连接断开和资源清理？
- 客户端断线：未连接时发送的消息是否触发了 Error 级别日志或回调通知，而非静默丢弃？
- 异常粒度：catch-all（裸 `catch` 或无异常类型过滤）是否替换为捕获特定异常类型？`catch` 作为流控是否已消除？

**检查方法：** 使用损坏的 protobuf 数据包发送到服务端，确认管线继续处理后续正常消息。强制断开客户端网络，确认服务端在超时后清理 session 和用户状态。

### 8.3 UI 渲染性能

**审查要点：**

- Per-frame 分配：`DoWindowContents` / `Draw` / `DoButton` 路径上是否有 `new` 对象？（Regex、TextWidget、GUIContent、List、HeightContainer 等）
- Regex：所有用于富文本标签剥离的 Regex 是否为 `static readonly` 预编译实例？（`RegexOptions.Compiled`）
- 布局缓存：`CalcHeight` / `CalcWidth` 是否在数据变更时计算一次并缓存，而非在 Draw 路径上每帧重新计算？
- LINQ 分配：Draw 路径上是否有 `.Where()` `.Sum()` `.Select()` `.ToList()` `.Count()` 等分配枚举器的 LINQ 调用？
- 属性 getter：属性 getter 是否在每帧被调用（如 `BadgeText`）且每次都执行计算或分配新对象？是否改为推送式缓存更新？
- 滚动列表：大型列表（聊天消息、交易物品）是否每帧遍历全部条目计算布局？是否引入脏标记跳过无变更时的重计算？

**检查方法：** RimWorld 开发者模式 → 打开 Performance Profiler → 进入服务器 Tab → 发送 100 条聊天消息 → 上下滚动 → 检查 GC.Alloc 和帧时间。每帧 GC 分配应接近零。

### 8.4 UI 适应性与健壮性

全量 UI 自适应（Phase 9 验收标准）要求系统在任意分辨率、不同 UI 缩放档位及极端内容尺寸下均保持布局稳定、控件可达、无文字穿透且性能良好。

**审查要点：**

- **屏幕安全区约束（Safe Area Clamping）**：所有独立主窗口及弹窗（`ServerTab`、`SettingsWindow`、`CredentialsWindow`、`TradeWindow`、`DirectTradeWindow`、红包详情窗口等）必须通过 `UiScreenSafeArea.ClampWindow` 限制在 `(0, 0, UI.screenWidth, UI.screenHeight)` 范围内。确保在从高分辨率切换到低分辨率、大 UI 缩放档位或多显示器切换时，窗口不超出屏幕边界，标题栏、拖动手柄、确认/关闭按钮永远可达。
- **动态导航与侧栏抽屉（Dynamic Navigation & Overflow）**：主 Tab 栏必须使用 RimWorld 原生 `TabDrawer.DrawTabsOverflow` 与 `TabDrawer.GetOverflowTabHeight`，保证在 10~20 个插件注册 Tab 时自动换行并由内容区动态扣除实际占用高度；侧栏在窗口可用宽度无法满足 `MAIN_MIN_WIDTH` (480px) + 侧栏 `MinimumWidth` 时，必须依据 `IResponsiveSidebarProvider.CanCollapse` 自动折叠为抽屉图标按钮（`☰`），点击弹出浮动抽屉，严禁挤压主内容区至不可用状态。
- **无负空间与弹性重排（Non-negative Geometry & Dynamic Reflow）**：所有布局输出 Rect 宽高必须严格非负（`UiScreenSafeArea.Normalize`）。表单使用 `ResponsiveFormLayout` 根据宽度在单行内嵌（Inline）与垂直堆叠（Stacked）间自适应切换，并预留错误信息高度；操作栏使用 `ResponsiveToolbarLayout` 在行数受限时将次要操作自动收纳进 `⋯` 溢出 FloatMenu；双栏布局使用 `ResponsiveSplitLayout` 在宽度或高度受限时降级为垂直排列或单窗格（SinglePane）子 Tab 切换。
- **长文本截断与滚动承载（Text Truncation & Tooltips）**：固定行高卡片/列表中的单行文本必须明确截断并挂载 `TooltipHandler.TipRegion`；多行文本必须基于宽度和数据版本缓存测量高度，并由外层 `Widgets.BeginScrollView` 承载，长玩家名、物品描述、长本地化翻译或服务器描述绝对不能覆盖操作按钮。
- **列表虚拟化（List Virtualization）**：聊天消息、交易货架、红包列表、人才列表、扩展日志等大型数据列表，必须使用 `VirtualListLayout`（定高 `GetFixedRange` 或变高 `GetDynamicRange`）做可见行裁剪，仅绘制视口可见项，禁止对全量条目执行 `Draw`。
- **缓存失效驱动（Cache Invalidation Driven）**：文本测量（`Text.CalcHeight` / `CalcSize`）、LINQ 排序（`OrderBy`）与复杂布局几何计算，必须由语言切换、容器尺寸变动或数据版本更新事件驱动，严禁在 `Draw` / `DoWindowContents` 热路径上逐帧重复计算或分配对象。
- **宿主中立与旧容器废弃（Host Neutrality & Obsolete Containers）**：所有响应式原语必须位于 `ClientExtensionAbstractions` 通用层，Host 不得针对特定业务硬编码分支；旧版 `Displayable` 弹性容器系列（`HorizontalFlexContainer`、`VerticalFlexContainer`、`TabsContainer`、`ConditionalContainer`、`MinimumContainer`、`VerticalPaddedContainer`）已全量标记 `[System.Obsolete]`，现有调用点必须做好非负尺寸保底防御，新代码禁止使用。

**检查方法：**
1. 在 1024×768、1280×720、1366×768、1920×1080、2560×1440 及不同 UI 缩放倍率下全屏/窗口化拖动测试。
2. 动态挂载 10~20 个 Tab、多个侧栏，验证 TabDrawer 换行与侧栏折叠抽屉交互。
3. 注入 64/128 字符长用户名、长物品名与长翻译文本，验证排版不重叠、无文字穿透。
4. 1000 条条目滚动性能压测，验证 GC.Alloc 保持近零、无卡顿掉帧。

### 8.5 线程安全

**审查要点：**

- 共享集合（Dictionary、List）的读写是否有 `lock` 保护或使用 `ConcurrentDictionary` / `ConcurrentQueue`？
- 网络回调（`OnPeerConnected`、`OnNetworkReceive` 等）在 poll 线程上触发时，操作 UI 或共享状态的代码是否封送至主线程？
- `Connected` 检查与 `Send` 之间是否存在 TOCTOU 竞态？是否使用 `TrySend` 代替 `Send`？

**检查方法：** 高并发连接测试（10 客户端同时连接+发送消息）→ 检查无 `InvalidOperationException`（集合已修改）、无崩溃。

## DLL 插件语言资源

宿主提供按插件包隔离的翻译服务，插件在 Activate 绑定、绘制时按 key 读取、Shutdown 释放。它不依赖商店或业务插件，不把托管语言注入 RimWorld 全局词典；语言切换由主线程发布，资源校验和回退是通用基础设施。

## 客户端程序集加载所有权

普通模组及其版本/条件有效目录由 RimWorld 选择和加载。客户端从游戏已加载的程序集中发现 Phinix 模块，不主动扫描其他模组根 `Assemblies` 或游戏程序目录。Phinix 主动加载范围依据自身 `ModContentPack.RootDir` 的运行库及 bundle 目录。

自身加载器先准备完整程序集身份，仅处理自身请求者的真实声明、完整匹配依赖，并在插件停止后撤销解析器。这是本加载器的所有权边界，不构成 CLR 隔离。托管插件载荷验证、启动冲突和依赖检查仍独立保留；服务端旧加载器待独立迁移验收。
